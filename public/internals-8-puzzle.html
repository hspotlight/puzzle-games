Sliding Puzzle — Game Overview

Game Design 8-puzzle

The Sliding Puzzle (also called the 8-puzzle or 15-puzzle) is one of the most studied problems in AI and search algorithms. The board is an n × n grid containing n² − 1 numbered tiles and one blank space. The player slides tiles into the blank to rearrange them into a goal configuration — typically sorted order with the blank in the bottom-right.

Rules:

  • Only tiles directly adjacent (up, down, left, right) to the blank can move.
  • A tile slides into the blank space — it cannot jump.
  • The puzzle is solved when tile 1 is at (0,0), tile 2 at (0,1), …, tile 8 at (2,1), blank at (2,2).

What makes it interesting algorithmically: not all tile arrangements are solvable. Exactly half of the 9! = 362,880 permutations of a 3×3 puzzle are reachable from any given start. The 15-puzzle (4×4) has over 10 trillion states — a BFS over the full space is intractable, making it a benchmark for heuristic search (A* with Manhattan distance is the classic approach).

Sliding Puzzle — Data Model

Data Structures

Three plain TypeScript interfaces model everything the game needs:

export interface Tile {
  id: string     // 'empty' for blank, 't1'–'t8' for numbered tiles
  value: number  // 0 for empty, 1–(n²−1) for numbered tiles
  row: number
  col: number
}

export interface GameState {
  gridSize: number
  tiles: Tile[]
  moves: number
  won: boolean
}

export interface MoveAction {
  tileId: string  // the numbered tile adjacent to empty that will slide
}

Why these fields?

Tile has both id and value: The id is a stable React key and map key (e.g., 't5' always refers to the tile with the number 5, regardless of where it currently sits). The value is what gets rendered on screen. Keeping them separate makes identity lookups O(1) via a Map.

Why not store the blank's position in GameState? The blank's row and col are available directly from the tile with value === 0. Duplicating that information would create an invariant that code everywhere must maintain — the classic "derived-data-in-state" trap. Instead, findEmpty(state) locates it in O(n²) time, which is negligible for a 3×3 board.

MoveAction identifies the tile, not the direction: Since the blank's position is known, the engine can compute the slide direction from tile.row − empty.row and tile.col − empty.col. This keeps the action minimal and direction-agnostic.

Key invariant: At all times, exactly one tile has value === 0 (the blank). All other tiles have unique positive values. The engine's applyMove preserves this by swapping the blank with the moving tile rather than creating or destroying tiles.

Sliding Puzzle — Key Algorithm

Algorithms

applyMove — immutable tile swap

applyMove is the heart of the engine. It validates the move, swaps the tile with the blank, increments the counter, and checks for the win — all without mutating anything:

export function applyMove(state: GameState, action: MoveAction): GameState {
  const tile = state.tiles.find(t => t.id === action.tileId)
  if (!tile || tile.value === 0) return state          // guard: empty can't "move"

  const empty = findEmpty(state)
  if (!isAdjacent(tile, empty)) return state           // guard: must be adjacent

  // Pure swap: tile goes where blank was, blank goes where tile was
  const newTiles = state.tiles.map(t => {
    if (t.id === action.tileId) return { ...t, row: empty.row, col: empty.col }
    if (t.value === 0)          return { ...t, row: tile.row,  col: tile.col  }
    return t  // all other tiles untouched — no array mutation
  })

  return { ...state, tiles: newTiles, moves: state.moves + 1,
           won: checkWin(newTiles, state.gridSize) }
}

The spread operator ({ ...t, ... }) creates new objects — neither the outer state nor any tile is ever mutated. This property is critical for the BFS solver, which stores many state snapshots concurrently and needs them to be independent.

checkWin — position-based win detection

Rather than comparing against a hardcoded solved array, the win check derives the expected position from each tile's value:

function checkWin(tiles: Tile[], gridSize: number): boolean {
  for (const tile of tiles) {
    if (tile.value === 0) {
      if (tile.row !== gridSize - 1 || tile.col !== gridSize - 1) return false
    } else {
      const idx = tile.value - 1          // tile 1 → index 0, tile 8 → index 7
      if (tile.row !== Math.floor(idx / gridSize) ||
          tile.col !== idx % gridSize) return false
    }
  }
  return true
}

For a 3×3 grid, tile 5 (value 5) should be at index 4 → row 1, col 1. This formula generalises to any grid size without hard-coding the target state, making the engine dimension-agnostic.

serializeState — canonical string for BFS deduplication

The BFS solver uses a Set<string> to track visited states. Two different GameState objects are logically identical if their tiles are in the same positions, regardless of array order. The canonical form sorts tiles by id before serializing:

export function serializeState(state: GameState): string {
  return state.tiles
    .slice()                               // don't mutate state.tiles
    .sort((a, b) => a.id.localeCompare(b.id))
    .map(t => `${t.value}:${t.row},${t.col}`)
    .join('|')
}
// Example output: "0:2,2|t1:0,0|t2:0,1|t3:0,2|t4:1,0|t5:1,1|t6:1,2|t7:2,0|t8:2,1"

Sliding Puzzle — CS Concepts

Computer Science

Graph search over an implicit state graph

The sliding puzzle is a classic example of searching an implicit graph: the graph is never fully materialised in memory. Instead, nodes (states) are generated on demand from the current node by calling getLegalMoves and applyMove. The solver traverses this graph using BFS (guarantees shortest path) or DFS (finds any path, potentially longer).

Reachability and parity

Not every permutation of tiles is reachable. For a 3×3 puzzle, the state space has two disconnected components of equal size (181,440 states each). A configuration is solvable if and only if the number of inversions (pairs where a larger tile precedes a smaller one in the flattened sequence, ignoring the blank) is even. Our levels are constructed by applying forward moves from the solved state, which guarantees reachability without needing to count inversions.

BFS vs DFS on the 8-puzzle

BFS explores states level-by-level (by move count) and always finds the optimal (fewest-move) solution. For the 8-puzzle, the maximum optimal solution depth is 31 moves, and the number of states BFS must explore in the worst case is around 181,000 — all of which fit comfortably in memory. DFS is faster per state but explores arbitrarily deep paths first; it finds a solution but not necessarily the shortest one. The solver caps exploration at 100,000 states as a safety valve for both algorithms.

State hashing and the visited set

Without a visited set, BFS would loop indefinitely (sliding tile A right then left returns to the original state, which would be queued again). The set stores canonical serializations so duplicate states are detected in O(1) amortized time per lookup. The cost of serializing each state is O(n²) — negligible for n = 3.

Immutability as a correctness tool

Every applyMove call returns a new state object. The BFS queue holds many state snapshots simultaneously; if any were mutated, previously-queued nodes would silently reflect the wrong game state. Immutability makes this class of bug impossible — each node in the queue owns its own slice of the game history.

This project uses 3×3 grids, keeping BFS tractable without heuristics. The solver explores at most 181,440 states — each serialized to a ~50-character string — fitting comfortably in a few megabytes of RAM and running in under 50ms in the browser.

Branching factor

The blank space has 2 neighbours in a corner, 3 on an edge, and 4 in the interior. The average branching factor for a 3×3 puzzle is approximately 2.67 (accounting for the no-backtrack constraint). The effective branching factor after deduplication is even lower because many short paths lead to the same state.

Why the 15-puzzle needs A*

BFS on the 15-puzzle would require storing ~10 trillion states — far beyond available RAM. The standard solution is A* search with the Manhattan distance heuristic: the sum over all tiles of |current_row − goal_row| + |current_col − goal_col|. This admissible heuristic guides the search toward the goal, exploring only a tiny fraction of the state space. Implementing A* for the 15-puzzle is a natural extension to this project.

Sliding Puzzle — Testing Strategy

Testing

Tests are co-located with source files in src/games/sliding-puzzle/. The engine tests cover every exported function with at least two test cases each; the level tests run the actual BFS solver against every handcrafted level.

engine.test.ts — property-based engine checks

buildOccupancy: Verifies that the 2D grid maps each tile's (row, col) to its id, that the blank's cell is null (not occupied), and that dimensions match gridSize. The blank-as-null invariant is critical: getMovableRange and the arrow-key handler both query the occupancy grid to find tiles adjacent to the blank.

getMovableRange: Tests all four adjacency cases (tile above, below, left, right of blank), a non-adjacent tile, a diagonally adjacent tile, and the blank itself. This covers the complete decision matrix for the function.

applyMove: Verifies position update of the sliding tile, position update of the blank, move counter increment, immutability of the original state (via JSON.stringify comparison before and after), identity return for invalid moves, win detection on the final move, and non-win for partial progress.

serializeState: Checks same-state consistency, different-state divergence, and order-independence by reversing the tile array and asserting the same canonical output.

getLegalMoves: Tests the three blank positions with known adjacency counts (center → 4, corner → 2), verifies which specific tile ids are included, and asserts that the blank tile itself is never returned.

// Example: verifying immutability
it('does not mutate the original state', () => {
  const originalTiles = JSON.stringify(L1.tiles)
  applyMove(L1, { tileId: 't5' })
  expect(JSON.stringify(L1.tiles)).toBe(originalTiles)
})

levels.test.ts — structural and solvability guarantees

For each of the five levels, four structural checks run first (no overlapping tiles, all tiles in bounds, exactly one blank, unique ids), then the most important check runs:

it(`level ${i + 1} is solvable`, { timeout: 10_000 }, () => {
  const result = solve(level)
  expect(result.solved).toBe(true)
})

This test actually runs the BFS solver and asserts solved === true. A level that looks valid by eye may still be in an unreachable permutation — only the solver can confirm solvability. For 3×3 puzzles, BFS completes in milliseconds, so the 10-second timeout is a safety net, not a performance target.

Run the tests From the project root: npm test to run once, or npm run test:watch to rerun on file changes. All 30 sliding-puzzle tests (25 engine + 25 level) run in under 200ms.

What is NOT tested

Drag interaction, click-to-slide, and arrow-key handling in the React components are not covered by unit tests. These interact with the Pointer Events API and DOM geometry in ways that are difficult to simulate accurately in a headless test environment. The engine tests ensure all game logic is correct; the UI layer is validated manually in the browser.
