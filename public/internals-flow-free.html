Flow Free — Internals

How a connect-the-dots puzzle is modeled, solved with BFS, and rendered in React.

React 19 TypeScript BFS / DFS Graph search Constraint satisfaction Vitest 4

Introduction

Overview

Flow Free is a grid-based puzzle where the player draws paths between colored endpoint pairs. Every cell on the board must be covered by exactly one path, and paths cannot cross. The challenge scales with grid size and number of colors.

From a CS perspective Flow Free is interesting because it is an NP-complete problem in the general case (it is a variant of the Hamiltonian path problem) yet small instances are tractable with BFS. The "fill every cell" constraint dramatically reduces the branching factor compared to solving without it — most partial paths that leave isolated pockets are immediately pruned by the solver heuristic.

Why this puzzle? Flow Free illustrates graph search, constraint satisfaction, path planning, and immutable state management all in a single small codebase — concepts that appear throughout systems design, robotics, and AI.

Rules & Objective

Game Design
  • The board is an N×N grid with colored dot-pairs (endpoints) placed at fixed positions.
  • The player draws a path between each pair of same-colored dots by dragging across adjacent cells (up/down/left/right — no diagonals).
  • Paths cannot cross or overlap. Stepping on a cell already occupied by another color is forbidden.
  • The puzzle is solved when every color has a completed path and every cell on the grid is covered by some path.

The "fill every cell" rule is what makes Flow Free algorithmically rich. Without it, each color could be connected trivially by a direct 2-cell path. The full-coverage constraint forces the solver to explore long, winding routes — and makes human play satisfying.

Type Definitions

Data Model

The data model is three plain TypeScript interfaces — no classes, no methods. All game logic lives in pure functions that accept and return these types.

// types.ts

export type ColorId = string  // e.g. 'red', 'blue', 'green'

export interface Endpoint {
  row: number
  col: number
  colorId: ColorId
}

export interface FlowPath {
  colorId: ColorId
  cells: Array<{ row: number; col: number }>  // ordered endpoint A → B
}

export interface GameState {
  gridSize: number
  endpoints: Endpoint[]   // fixed — never changes during a level
  paths: FlowPath[]       // one entry per active color
  moves: number
  won: boolean
}

export interface MoveAction {
  colorId: ColorId
  cells: Array<{ row: number; col: number }>  // replaces existing path for this color
}

Why no occupancy in GameState?

The occupancy grid (which cell is owned by which color) is a function of paths — it is derived data. Storing it in GameState would create redundancy: two sources of truth that must be kept in sync. Instead, buildOccupancy(state) recomputes it on demand in O(N²) time, which is negligible for typical puzzle sizes.

Immutability invariant Every function that returns a GameState must return a new object. applyMove uses the spread operator: { ...state, paths: newPaths, moves: state.moves + 1, won }. Never call .push() or .splice() on a state array — create a new array instead.

Occupancy Grid

Engine

buildOccupancy is the central utility function in the engine. It converts the list of paths into a 2D array where each cell contains either the ColorId of the path passing through it, or null if the cell is empty.

export function buildOccupancy(state: GameState): (ColorId | null)[][] {
  const grid = Array.from({ length: state.gridSize }, () =>
    new Array(state.gridSize).fill(null)
  )
  for (const path of state.paths) {
    for (const cell of path.cells) {
      grid[cell.row][cell.col] = path.colorId
    }
  }
  return grid
}

This function is called inside getLegalMoves, checkWin, and the React rendering layer. Because it is pure and creates a fresh array each time, it can be called freely without caching concerns.

Time complexity

Building occupancy takes O(P) time where P is the total number of path cells across all colors. For a fully-covered N×N board, P = N², so building occupancy is O(N²). Checking a single cell for occupancy is then O(1).

Path Drawing

Engine UI

A path is a sequence of cells forming a connected chain from one endpoint to the other. The key design decision: a MoveAction carries the entire new cell list for a color — not an incremental delta. This means the reducer is trivially simple:

export function applyMove(state: GameState, action: MoveAction): GameState {
  // Remove old path for this color, add new one
  const newPaths = state.paths.filter(p => p.colorId !== action.colorId)
  if (action.cells.length > 0) {
    newPaths.push({ colorId: action.colorId, cells: action.cells })
  }
  const newState = { ...state, paths: newPaths, moves: state.moves + 1, won: false }
  newState.won = checkWin(newState)
  return newState
}

The drag interaction in the React component builds up the new cell list incrementally — appending cells as the pointer moves — then dispatches a single action per frame via requestAnimationFrame.

Backtracking while dragging

When the pointer moves back to the second-to-last cell in the current path, the UI truncates the path by one — this feels like "erasing" the last segment and is implemented by slicing the array: path.cells.slice(0, -1).

Win Condition

Engine

Winning requires two simultaneous conditions to be true:

  1. Every color is connected — for each color, a path exists whose first cell is one endpoint and last cell is the other.
  2. Full coverage — every cell in the N×N grid belongs to some path (no nulls in the occupancy grid).
function checkWin(state: GameState): boolean {
  const colors = [...new Set(state.endpoints.map(e => e.colorId))]
  for (const color of colors) {
    const path = state.paths.find(p => p.colorId === color)
    if (!path || !isPathComplete(path, state)) return false
  }
  const occ = buildOccupancy(state)
  let covered = 0
  for (let r = 0; r < state.gridSize; r++)
    for (let c = 0; c < state.gridSize; c++)
      if (occ[r][c] !== null) covered++
  return covered === state.gridSize * state.gridSize
}
Why check coverage separately? A player could connect all colors with short direct paths yet leave half the board empty. The coverage check is what forces the satisfying "pipe fills the whole board" constraint — and what makes the puzzle genuinely hard.

Legal Moves

Engine Algorithm

getLegalMoves(state) enumerates every valid next action from the current state. The BFS solver calls this at each node to expand the search frontier.

For each color, the legal extensions are:

  • Extend from the head of the current path to any adjacent empty cell (or the target endpoint)
  • Extend from the tail symmetrically
  • Start fresh if no path exists yet, from either endpoint

A move is illegal if it would step onto a cell already occupied by a different color, revisit a cell in the same path, or move diagonally. The solver never emits "clear path" actions — clearing increases state space without making progress toward a solution.

State explosion For a 5×5 board with 5 colors the branching factor at each node is roughly 3–4 (each path tip has 3–4 neighbors, minus backtracking). A naive BFS can easily exceed 100k states — set a generous maxStates limit (500k) and accept that very large grids may not be solved interactively.

BFS Solver

Algorithm

The solver is game-agnostic: it only calls getLegalMoves, applyMove, and serializeState. This means the same solver module could power any puzzle that exposes those three functions.

export function solve(
  initial: GameState,
  algorithm: SolverAlgorithm = 'bfs',
  maxStates = 200_000
): SolverResult {
  const visited = new Set<string>()
  const queue = [{ state: initial, moves: [] }]
  visited.add(serializeState(initial))

  while (queue.length > 0) {
    const node = algorithm === 'bfs' ? queue.shift() : queue.pop()
    for (const action of getLegalMoves(node.state)) {
      if (action.cells.length === 0) continue  // skip clear-path actions
      const next = applyMove(node.state, action)
      const key = serializeState(next)
      if (visited.has(key)) continue
      visited.add(key)
      if (next.won) return { solved: true, moves: [...node.moves, action], statesExplored }
      queue.push({ state: next, moves: [...node.moves, action] })
    }
  }
  return { solved: false, moves: [], statesExplored }
}

serializeState — the deduplication key

The BFS needs to detect when two different search paths arrive at the same game state. serializeState converts the paths into a canonical string by sorting paths by colorId and joining cell coordinates. Two states are identical iff their serializations match.

export function serializeState(state: GameState): string {
  return [...state.paths]
    .sort((a, b) => a.colorId.localeCompare(b.colorId))
    .map(p => `${p.colorId}:${p.cells.map(c => `${c.row},${c.col}`).join(';')}`)
    .join('|')
}

State Space Analysis

Algorithm

Flow Free is NP-complete in general: deciding whether a given board is solvable is as hard as solving it, and the state space grows super-polynomially with board size. However, for the small instances used in this implementation (4×4 to 6×6) BFS is practical.

The "fill every cell" constraint acts as a natural pruning heuristic: any path arrangement that creates an isolated empty region unreachable from any path head can be immediately discarded. Production Flow Free solvers use constraint propagation (like AC-3 or lookahead) to prune these dead ends without fully exploring them.

Hamiltonian path connection The full-coverage requirement is equivalent to requiring that the union of all paths forms a Hamiltonian cover of the grid graph — visiting every vertex exactly once across all paths. This is why the problem is NP-complete: Hamiltonian path is a classic NP-complete graph problem.

Testing Strategy

Testing

Two test files cover the implementation at different layers:

engine.test.ts — unit tests for pure functions

Every exported function in engine.ts is tested in isolation. The tests verify:

  • buildOccupancy: correct cells filled, nulls for empty cells, correct grid dimensions
  • getNeighbors: correct count for corners, edges, and center cells; no out-of-bounds results
  • applyMove: path replacement, move counter increment, immutability (original unchanged via JSON.stringify), win detection
  • serializeState: determinism, order-independence (same state regardless of path array order)
  • getLegalMoves: extends paths, never steps on occupied cells of other colors

levels.test.ts — integration tests per level

For each level in LEVELS the test suite checks:

  1. No two path cells overlap at the same (row, col) — each position is unique.
  2. Every color has exactly 2 endpoints.
  3. All endpoints are within the grid bounds.
  4. The BFS solver finds a solution within a generous state limit — if this fails the level is unsolvable as designed.
