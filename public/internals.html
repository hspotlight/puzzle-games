Unblock Me — Game Internals

A deep dive into how a browser puzzle game is built: data structures, movement algorithms, drag interactions, and graph-search solvers — written for CS students who want to understand the code.

React 19 TypeScript Vite Vitest BFS / DFS Pointer Events API requestAnimationFrame

Introduction

Game Design

Unblock Me (also known as Rush Hour) is a sliding-block puzzle. The board is a 6×6 grid. One special target block (the red one) must slide out through an exit hole on the right wall. Other blocks obstruct the path — the player must slide them out of the way.

Rules are simple:

  • Horizontal blocks slide left / right only.
  • Vertical blocks slide up / down only.
  • No block can pass through another.
  • The puzzle is solved when the target block exits the right edge.

Despite these simple rules, the state space is large enough that many puzzles require careful planning — and a computer solver needs a proper graph-search algorithm to find the solution.

Type Definitions

types.ts

Everything the game needs to represent a puzzle state lives in three interfaces. Notice there are no methods — just plain data. This is deliberate: pure data is trivially serialisable, comparable, and copyable.

// types.ts
export type Direction = 'horizontal' | 'vertical'

export interface Block {
  id:        string      // unique id, e.g. 'target', 'vA', 'hB'
  row:       number      // top-left row (0-indexed)
  col:       number      // top-left col (0-indexed)
  length:    number      // cells occupied (always ≥ 2)
  direction: Direction
  isTarget:  boolean     // true for the red block
}

export interface GameState {
  gridSize: number       // always 6 in this game
  blocks:   Block[]
  exitRow:  number       // row where the target must reach the right edge
  moves:    number       // move counter
  won:      boolean
}

export interface MoveAction {
  blockId: string        // which block to move
  delta:   number        // positive = right/down; negative = left/up
}

The Grid — Occupancy Map

engine.ts · buildOccupancy()

The GameState only stores the list of blocks. It does not store which cells are free or occupied. To answer "is cell (r, c) taken?" the engine builds a 2D lookup table on demand — the occupancy map.

function buildOccupancy(state: GameState): (string | null)[][] {
  // Create a gridSize × gridSize matrix, all null
  const grid = Array.from({ length: state.gridSize }, () =>
    Array(state.gridSize).fill(null)
  )

  for (const block of state.blocks) {
    for (let i = 0; i < block.length; i++) {
      // For vertical blocks: advance down rows; for horizontal: advance across cols
      const r = block.direction === 'vertical'   ? block.row + i : block.row
      const c = block.direction === 'horizontal' ? block.col + i : block.col
      grid[r][c] = block.id   // mark cell with the block's id
    }
  }
  return grid
}
Why a 2D array and not a Set? A 2D array gives O(1) cell lookup — grid[r][c]. A Set of strings like "2,3" would be O(1) average too, but indexing an array is faster in practice because there's no string allocation or hash computation on every access.

Level Design

levels.ts

Each level is a GameState snapshot defined as a plain object. A tiny helper function avoids repeating the fixed fields:

function level(exitRow: number, blocks: Block[]): GameState {
  return { gridSize: 6, exitRow, moves: 0, won: false, blocks }
}

// Level 1 — 3 moves to solve
export const LEVEL_1 = level(2, [
  { id: 'target', row: 2, col: 0, length: 2, direction: 'horizontal', isTarget: true  },
  { id: 'vA',     row: 1, col: 2, length: 2, direction: 'vertical',   isTarget: false },
  { id: 'vB',     row: 2, col: 4, length: 2, direction: 'vertical',   isTarget: false },
  // … more blocks …
])

Levels 1–10 are progressively harder. The key design dimension is dependency depth — how many "chain" moves are needed before you can clear the path:

LevelsOptimal MovesPattern
1–23Independent single blockers — each moves freely
3–44–5One-level chain — block A blocks blocker B
5–75–6Two-chain puzzles, non-obvious exit row
8–106–7Interleaved chains, multiple sub-puzzles
Design tip Every level in levels.ts has a comment above it showing the exact solution path (e.g. vA↑1, vB↓1, target→4). When you add new levels, write the solution first, then place the blocks to create it — this is much easier than placing blocks randomly and hoping a solution exists.

All 10 levels are automatically validated by levels.test.ts: it checks that no two blocks overlap and that BFS can solve every level.

Block Movement Algorithm

engine.ts · getMovableRange() · applyMove()

Step 1 — getMovableRange()

Before applying any move, the engine calculates how far a block can travel in each direction. It scans outward from the block's edges, counting free cells until it hits a wall or another block.

function getMovableRange(block: Block, state: GameState): { min: number; max: number } {
  const grid = buildOccupancy(state)
  let min = 0, max = 0

  if (block.direction === 'horizontal') {
    // Scan LEFT from left edge
    let c = block.col - 1
    while (c >= 0 && grid[block.row][c] === null) { min--; c-- }

    // Scan RIGHT from right edge
    c = block.col + block.length
    while (c < state.gridSize && grid[block.row][c] === null) { max++; c++ }
  } else {
    // Vertical: scan UP and DOWN
    let r = block.row - 1
    while (r >= 0 && grid[r][block.col] === null) { min--; r-- }
    r = block.row + block.length
    while (r < state.gridSize && grid[r][block.col] === null) { max++; r++ }
  }

  return { min, max }   // e.g. { min: -2, max: 1 }
}

For example: a vertical block at rows 1–2 in a column with free cells at row 0 (above) and rows 3–4 (below) returns { min: -1, max: 2 }.

Step 2 — applyMove()

Once we know the legal range, applyMove clamps the requested delta and creates a new state object. It never mutates the old one.

function applyMove(state: GameState, action: MoveAction): GameState {
  const block = state.blocks.find(b => b.id === action.blockId)
  if (!block) return state

  const { min, max } = getMovableRange(block, state)
  const clampedDelta = Math.max(min, Math.min(max, action.delta))
  if (clampedDelta === 0) return state        // no-op

  // Map over blocks — only the moved block gets new coordinates
  const newBlocks = state.blocks.map(b => {
    if (b.id !== action.blockId) return b
    return {
      ...b,
      row: b.direction === 'vertical'   ? b.row + clampedDelta : b.row,
      col: b.direction === 'horizontal' ? b.col + clampedDelta : b.col,
    }
  })

  // Check win: target's right edge has cleared the board
  const target = newBlocks.find(b => b.isTarget)!
  const won = target.direction === 'horizontal'
    && target.col + target.length >= state.gridSize

  return { ...state, blocks: newBlocks, moves: state.moves + 1, won }
}
Clamping is a safety net, not the primary guard The UI already constrains drag and click to legal positions before calling onMove. The clamp inside applyMove is a second line of defence — it makes the engine safe to call from the solver or tests without trusting the caller.

Win Condition

engine.ts

The win check is a single boolean expression evaluated after every move:

const won = target.direction === 'horizontal'
          && target.col + target.length >= state.gridSize
// Example: col=4, length=2, gridSize=6 → 4+2=6 ≥ 6 → won!

The target block "exits" as soon as its right edge reaches or passes column 6 (the wall). There's no special exit animation state — the won flag in GameState is enough for the UI to show the win banner.

Immutable State

Functional Core

Every function in engine.ts is pure: given the same inputs, it always returns the same output, and it never modifies its arguments. This pattern — sometimes called a "functional core, imperative shell" — has concrete engineering benefits:

BenefitHow it helps
TestabilityCall the function directly in a test — no mocking, no setup
Time travelKeep a stack of states → free undo support
Concurrency-safeNo shared mutable state → no race conditions
Solver-friendlyThe BFS solver can call applyMove in a tight loop without side effects

Immutability in practice: the spread operator ({ ...state, blocks: newBlocks }) creates a shallow copy. Since blocks is an array of simple objects with no nested references, a shallow copy is sufficient.

useReducer Pattern

UnblockMe.tsx

The top-level game page manages state with React's useReducer hook. A reducer is a function (state, action) → newState — the same pattern used by Redux, but built into React with no extra library.

type Action =
  | { type: 'LOAD_LEVEL';   index: number }
  | { type: 'MOVE';         action: MoveAction }
  | { type: 'SELECT';       id: string | null }
  | { type: 'SET_STATE';    state: GameState }  // used during solver animation

function reducer(page: GamePageState, action: Action): GamePageState {
  switch (action.type) {
    case 'LOAD_LEVEL': return {
      levelIndex: action.index,
      state: LEVELS[action.index],
      selectedBlockId: null,
    }
    case 'MOVE': return {
      ...page,
      state: applyMove(page.state, action.action),
      selectedBlockId: null,
    }
    case 'SELECT': return { ...page, selectedBlockId: action.id }
    case 'SET_STATE': return { ...page, state: action.state }
    default: return page
  }
}
Why useReducer instead of useState? When multiple pieces of state always change together (level index + game state + selection), a reducer bundles them into one atomic update. It also makes every state transition explicit and named — much easier to reason about and test than scattered setState calls.

Drag System with requestAnimationFrame

Grid.tsx · Pointer Events API

Dragging a block involves three events: pointerdown, pointermove, and pointerup. The key challenge is making it feel smooth without causing excessive React re-renders (which would stutter on every pixel moved).

The approach: decouple visual state from committed state

  1. pointerdown — Record the drag start position, compute { min, max } once via getMovableRange, store everything in a useRef (no re-render).
  2. pointermove — Calculate the raw pixel delta, convert to cell delta, clamp to legal range. If the cell delta changed, schedule a requestAnimationFrame to update visual state. Skip if a frame is already queued.
  3. pointerup — Cancel any pending frame, commit the final delta by calling onMove (which dispatches to the reducer).
const handlePointerMove = useCallback((e: React.PointerEvent) => {
  if (!dragRef.current) return
  const ds = dragRef.current
  const block = blockMap.get(ds.blockId)
  if (!block) return

  // Convert pixel offset → cell delta
  const rawPx = block.direction === 'horizontal'
    ? e.clientX - ds.startX : e.clientY - ds.startY
  const rawDelta = Math.round(rawPx / (cellSize + GAP))
  const clamped = Math.max(ds.min, Math.min(ds.max, rawDelta))

  if (clamped === ds.currentDelta) return   // cell unchanged, skip
  ds.currentDelta = clamped

  // Throttle React re-renders to animation frames (≤ 60 per second)
  if (rafRef.current !== null) return       // frame already queued
  rafRef.current = requestAnimationFrame(() => {
    rafRef.current = null
    if (dragRef.current)
      setDragVisual({ blockId: dragRef.current.blockId, delta: dragRef.current.currentDelta })
  })
}, [blockMap, cellSize])
requestAnimationFrame (RAF) throttling pointermove can fire hundreds of times per second. RAF ensures we only update React state at most once per screen refresh (~60 Hz). This is a standard technique for smooth, non-janky drag interactions. The latest delta is always committed because dragRef.current.currentDelta is updated synchronously — the RAF closure captures the ref, not a stale value.

Pointer Capture

On pointerdown, the code calls element.setPointerCapture(e.pointerId). This makes the element receive all future pointer events even if the cursor leaves its bounds — essential for smooth drag-outside-the-grid behaviour.

Input Methods

Grid.tsx

Three independent input methods are implemented, all converging on the same onMove(action) callback:

MethodHow it works
Drag Pointer events (works on touch and mouse). Snap-to-grid: visual is continuous, commit is discrete cells.
Click-to-move Click a block to select it (highlights orange). Click anywhere on the grid to move it to that position. Delta = clicked cell − block's anchor cell, clamped to legal range.
Arrow keys When a block is selected, arrow keys move it by 1 cell. Only the axis matching the block's direction is processed (e.g. Left/Right for horizontal blocks). 
// Click-to-move: calculate delta from click position
function handleGridClick(e: React.MouseEvent<HTMLDivElement>) {
  if (!selectedBlockId) return
  const rect = e.currentTarget.getBoundingClientRect()
  const x = e.clientX - rect.left - PADDING
  const y = e.clientY - rect.top  - PADDING
  const clickCol = Math.floor(x / (cellSize + GAP))
  const clickRow = Math.floor(y / (cellSize + GAP))
  let delta = block.direction === 'horizontal'
    ? clickCol - block.col : clickRow - block.row
  const clamped = Math.max(min, Math.min(max, delta))
  if (clamped !== 0) onMove({ blockId: selectedBlockId, delta: clamped })
}

Rendering

Grid.tsx

Absolute positioning

Blocks are positioned with position: absolute inside a position: relative container. Each block's pixel position is computed from its grid coordinates:

const GAP     = 6   // px between cells
const PADDING = 16  // px inset from grid edge

// Block top-left position in pixels:
const baseTop  = block.row * (cellSize + GAP)
const baseLeft = block.col * (cellSize + GAP)

// If dragging, offset by dragDelta cells:
const top  = block.direction === 'vertical'   ? baseTop  + dragDelta * (cellSize + GAP) : baseTop
const left = block.direction === 'horizontal' ? baseLeft + dragDelta * (cellSize + GAP) : baseLeft

// Block pixel dimensions:
const w = block.direction === 'horizontal'
  ? block.length * cellSize + (block.length - 1) * GAP : cellSize
const h = block.direction === 'vertical'
  ? block.length * cellSize + (block.length - 1) * GAP : cellSize

Memoisation

Two sub-components are wrapped in React.memo():

  • CellGrid — the background grid of cells. Re-renders only when gridSize or cellSize changes (never during normal gameplay).
  • BlockPiece — a single block. Re-renders only when its own props change (position, drag state, selection).

This means moving one block only re-renders that one block, not all blocks. For a 6×6 grid this is a minor optimisation, but it demonstrates the pattern for larger grids.

Responsive cell size

A useCellSize() hook watches the window dimensions and returns a cell size between 44 px and 64 px, so the grid fits on any screen from a small phone to a wide monitor.

BFS vs DFS Solver

solver.ts · Graph Search

The puzzle state space is a graph: each node is a GameState, each edge is a legal move. Finding the solution means finding a path from the initial node to a won node.

The solver implements both BFS and DFS with a single function — the only difference is how the queue is accessed:

function solve(
  initial: GameState,
  algorithm: 'bfs' | 'dfs' = 'bfs',
  maxStates = 100_000
): SolverResult {
  if (initial.won) return { solved: true, moves: [], statesExplored: 0 }

  const visited = new Set<string>()
  const queue: SearchNode[] = [{ state: initial, moves: [] }]
  visited.add(serializeState(initial))

  while (queue.length > 0) {
    // BFS = shift (FIFO queue) → shortest path
    // DFS = pop  (LIFO stack) → any path
    const node = algorithm === 'bfs' ? queue.shift() : queue.pop()

    for (const action of getLegalMoves(node.state)) {
      const next = applyMove(node.state, action)
      const key  = serializeState(next)
      if (visited.has(key)) continue  // already explored
      visited.add(key)

      const path = [...node.moves, action]
      if (next.won) return { solved: true, moves: path, statesExplored }
      queue.push({ state: next, moves: path })
    }
  }
  return { solved: false, moves: [], statesExplored }
}

BFS vs DFS — when to use each

BFSDFS
Queue typeFIFO (shift)LIFO (pop)
ExploresLevel by level (nearest first)One branch as deep as possible
GuaranteesShortest solutionA solution (not necessarily optimal)
MemoryO(bd) — can be largeO(d) — very small
Best forMinimum-move puzzle solutionsChecking if a solution exists quickly
The visited set is critical Without the visited set, the solver would loop forever: moving block A right then left returns to the same state. The set stores serialized state strings and skips any state already seen. This transforms an infinite cycle into a finite DAG traversal.

State Hashing

engine.ts · serializeState()

Two GameState objects represent the same board position if every block is in the same cell. Since blocks is a JavaScript array, direct equality (===) won't work — two different array objects can have the same contents. Instead, we serialize the state to a canonical string:

function serializeState(state: GameState): string {
  return state.blocks
    .slice()                              // copy so sort doesn't mutate
    .sort((a, b) => a.id.localeCompare(b.id)) // canonical order
    .map(b => `${b.id}:${b.row},${b.col}`)  // "id:row,col"
    .join('|')
}
// Example output:
// "hC:4,1|h0:0,3|h5:5,2|target:2,0|vA:1,2|vB:2,4|vD:3,0"

The sort ensures that two states with blocks in the same positions but different array orders produce the same string. The string is then used as a key in a JavaScript Set<string>, which has O(1) average insert and lookup.

Alternative: Zobrist hashing For very large state spaces, you'd use Zobrist hashing — XOR a random 64-bit number for each (block, position) pair. It's faster than string concatenation and avoids memory allocation. For a 6×6 grid with ~10 blocks, string hashing is plenty fast.

Complexity Analysis

Theory

State space size

An upper bound: each block occupies 1 row or column and can slide within it. In a 6-cell row, a block of length 2 has 5 positions. With ~10 blocks, the theoretical maximum is roughly 510 ≈ 10 million states. In practice, collisions between blocks reduce this dramatically — typical levels have a few thousand reachable states.

Solver complexity

TimeSpace
BFSO(V + E)O(V) — stores all reachable states
DFSO(V + E)O(d) — stores one path at a time

Where V = number of unique states, E = number of transitions (legal moves), d = depth of solution. The solver caps exploration at 100,000 states to prevent the UI from freezing on unsolvable or extremely complex inputs.

Engine function complexity

FunctionComplexityNotes
buildOccupancyO(n · L)n blocks, L avg length (≈2–3)
getMovableRangeO(G)G = gridSize, scanning one row/col
applyMoveO(n)Maps over all blocks
getLegalMovesO(n · G)Range for every block
serializeStateO(n log n)Dominated by sort
